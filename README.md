The project does **not** re-implement PHMN. Following the supervisor's direction, it takes the
authors' own implementation as the reference, decomposes it into its eleven components, and
measures what each component actually contributes. Along the way the published implementation
turned out to miss correct answers, for two reasons: one defect of the code and one of the paper
itself. The repository contains the patch, the evidence that the patched build is correct, and the
experiments that quantify the consequences. Decomposing the item order showed that placing
positive items first, as the earlier algorithm FHN does, changes no answer and makes the patched
build match the runtimes the paper publishes for `pumsb_negative` at all five thresholds, where
the order of the code is 119 to 393 times slower (Sections 7.5 and 7.10 of the report).

The written report is `523H0159_523H0169_week11.docx`. Chapter 7 of that report contains every
number produced by the code in this repository.

## 3. Quick start — reproduce the three headline results

### 3.1 Compile the patched classes

```
javac -nowarn -cp tools/spmf/spmf.jar -d build/patched src/patched/ca/pfv/spmf/algorithms/frequentpatterns/phmn_plus/*.java
```

This writes eight `.class` files into `build/patched`. Nothing inside `spmf.jar` is modified; the
patched build is selected by putting `build/patched` **first** on the classpath, so Java loads it
instead of the copy in the jar. That is the only trick used throughout the project.

### 3.2 Reproduce the worked example of the paper — expect exactly 5 patterns

```
java -jar tools/spmf/spmf.jar run PHMN data/PHMN_Table1_example.txt output/t1.txt 30 1 5 1 3
```

The five trailing numbers are, in order, `minUtil minPer maxPer minAvg maxAvg`.

### 3.3 The defect — the published build returns nothing on real data

```
java -Xmx6g -cp "tools/spmf/spmf.jar" ca.pfv.spmf.gui.Main run PHMN data/chess_negative.txt output/stock.txt 150000 1 3196 1 3196
```

`output/stock.txt` is empty: **0 patterns, 0 candidates**, in a quarter of a second.

### 3.4 The patch — same data, same parameters, 13 patterns

```
java -Xmx6g -cp "build/patched;tools/spmf/spmf.jar" ca.pfv.spmf.gui.Main run PHMN data/chess_negative.txt output/patched.txt 150000 1 3196 1 3196
```

**13 patterns** from 20,086 candidates, in about two seconds. The two commands differ **only** in
`-cp`. The console banner reads `v2.38-PATCHED` when the patched build is loaded, so there is never
any doubt about which one ran. At `minUtil` 80,000, the level used in Section 7.3 of the report,
the published build still returns 0 patterns while the patched build returns 70,923, but needs
about twenty minutes.

### 3.5 Evidence that the patch is correct, not merely more productive

```
py -I analysis/spmf_phmn_stress_test.py tools/spmf/spmf.jar
py -I analysis/spmf_phmn_stress_test.py tools/spmf/spmf.jar --patched build/patched
py -I analysis/spmf_phmn_stress_test.py tools/spmf/spmf.jar --patched build/patched --chu-ky
```

The script generates 60 small databases, 56 of which contain negative utilities, enumerates
**every** itemset by brute force to obtain the correct answer, and compares itemset by itemset and
on utility, support, `minPer` and `maxPer`. Expected outcome: the published build misses 213 of
1,224 correct patterns; the patched build misses none, reports none too many and no wrong value.
The third command repeats the comparison under three tight periodicity settings per database, 180
runs, so that the periodicity thresholds come into play as well; the patched build again matches on
all 1,106 patterns. The log also counts how often the thresholds change the answer compared with the
utility threshold alone (166 of the 180 runs), and how often `maxPer` or `maxAvg`, the only two that
prune, do so (131). These counts are taken on the output; the pruning branches are not instrumented.
The loose pass is not entirely neutral: `minAvg = 1` filters out an itemset present in every
transaction, since its average period is `|D| / (|D| + 1) < 1`. That removes two itemsets over the
60 databases, in the brute force and in SPMF alike. `minPer` follows the SPMF convention, gaps between
consecutive occurrences only (Section 5.11 of the report). Each command takes two to three minutes and exits with status 1 on any difference,
so the first command, on the published build, is expected to end with status 1.
These tests are evidence of correctness on the inputs tried, not a proof for every input.

## 4. The patch

Three files. Every line that changes the behaviour is marked `PATCHED`; the other differences
from the stock source are Javadoc comments and three empty constructors that the Javadoc check
asks for.

**Root cause: two defects, one in the code and one in the paper.** PHMN prunes a branch by
computing an upper bound on the utility attainable in that branch and discarding the branch when
the bound falls below `minUtil`. A bound is only valid if it is never lower than the real value.

1. *In the code.* Definition 8 of the paper defines the remaining utility `RU` with the
   **positive** items placed after the itemset only. The published code lets the negative
   utilities enter `RU` as well. The same line also feeds the pair TWUs of EUCS with the signed
   transaction utility, where Definition 6 uses the positive one.
2. *In the paper.* Strategy 4 of the paper prunes when `U(X) + RU(X) < minUtil`, where `U` is the
   signed utility, and the code implements exactly that test. The proof of Strategy 4 overlooks
   that an extension occurs in only some of the transactions of `X`; dropping a transaction in
   which `X` is negative makes the sum larger. Smallest counterexample, shipped as
   `data/strategy4_counterexample.txt`: `T1 = {x:-100}`, `T2 = {x:-1, y:+10}`, `minUtil = 5`.
   `U(x) + RU(x) = -91`, so `x` is pruned, yet `U({x,y}) = 9`.

The patch fixes both: `RU` and the pair TWUs take positive utilities only, and the test becomes
`PU(X) + RU(X)`, at the gate of each subtree and in LA-prune, where
`PU` is the sum of the *positive* utilities of `X` only. That test is valid because every term
it sums is non-negative, so dropping transactions can only lower it; the proof is in Section 5.2.2
of the report.

**Separating the two.** `src/strategy4/` fixes defect 1 and keeps defect 2. Against brute force on
the 60 generated databases, the published build misses 213 of 1,224 patterns, `strategy4` misses
22, and the patched build misses none:

```
py -I tools/sinh_strategy4.py
javac -nowarn -cp tools/spmf/spmf.jar -d build/strategy4 src/strategy4/ca/pfv/spmf/algorithms/frequentpatterns/phmn_plus/*.java
py -I analysis/spmf_phmn_stress_test.py tools/spmf/spmf.jar                          > output/runs/stress_60db_stock.log
py -I analysis/spmf_phmn_stress_test.py tools/spmf/spmf.jar --patched build/strategy4 > output/runs/stress_60db_strategy4.log
py -I analysis/spmf_phmn_stress_test.py tools/spmf/spmf.jar --patched build/patched   > output/runs/stress_60db_patched.log
java -cp "build/strategy4;tools/spmf/spmf.jar" ca.pfv.spmf.gui.Main run PHMN data/strategy4_counterexample.txt output/ce.txt 5 0 10 0 10
```

The last command returns `{y}` alone; with `build/patched` in its place it returns `{y}` and
`{x, y}`.

**Concrete instance of defect 1.** On `chess_negative`, item 46 has a true utility of 84,390 and
occurs very regularly, but the bound the published code computes for it is **−354,580**, so its
whole branch is cut. Item 46 is positive in every transaction, so here `U = PU` and the whole error
comes from the negative terms in `RU`. At `minUtil` 80,000 the published build therefore reports 0 patterns.

**The fix.**

* `ElementPHMN.java` — a new final field `putils` holding the positive utility of the itemset in
  that transaction, plus a four-argument constructor. The three-argument constructor is kept so
  that unrelated SPMF code still compiles.
* `UtilityListPHMN.java` — accumulate `sumPutils` alongside `sumIutils`.
* `AlgoPHMN.java` — the two defects surface in five places: only positive utilities may
  enter `remainingUtility`; the TWU used by EUCP is the positive transaction utility; the subtree
  gate and the LA-prune accumulator both use `sumPutils + sumRutils`; and `putils` is maintained
  additively when utility lists are joined. The version banner becomes `v2.38-PATCHED`.

To see the patch itself:

```
diff -u tools/spmf/source/ca/pfv/spmf/algorithms/frequentpatterns/phmn_plus/AlgoPHMN.java src/patched/ca/pfv/spmf/algorithms/frequentpatterns/phmn_plus/AlgoPHMN.java
```

To check the documentation, run the `javadoc` of JDK 25 with every check enabled. It reports
no error and no warning on the corrected classes and the three clients:

```
javadoc -encoding UTF-8 -Xdoclint:all -private -quiet -cp tools/spmf/spmf.jar -d build/javadoc src/patched/ca/pfv/spmf/algorithms/frequentpatterns/phmn_plus/*.java src/ClientAblationPHMN.java src/ClientDomainPHMN.java src/ClientOrderPHMN.java
```

The `javadoc` found first on the `PATH` must be the one of JDK 25; an older one cannot read
`spmf.jar` and stops with "class file has wrong version".

### Every number in the report can be traced back, and checked

Every measured number in Chapter 7 of the report comes from a file in this repository: a row of a
CSV file under `output/`, or a console log under `output/runs/` named in the table above. The text
of the report was written by the team; the numbers in it were copied from those files, and the
files are what to check them against.

`output/do_luong.csv` holds one row per run on the real datasets. Besides the parameters and the
results, each row carries a `file_mau` column naming the pattern file that run produced and a
`file_log` column naming its raw console log. Four early rows, measured before logging was in
place, have no log, and each of those configurations was measured again later with a log. For
the two runs of the published build the report uses the later rows. For the two runs of the
patched build on `accidents_negative` at 18,000,000 and 17,000,000 it keeps the early rows, so
that the five levels of its Table 7.3 are compared under the conditions of one session; the later
rows reproduce their pattern and candidate counts exactly, with runtimes 1.30 and 1.51 times
higher. Section 7.14 of the report explains why runtimes of different days differ by that much.

`output/e8_do_luong.csv` does the same for the 96 runs of experiment E8, and adds the pruning
counters. Three of its columns exist purely to be checked. `bat_bien` records whether the program's
own self-test `pairsConsidered = rejEUCP + rejESCP + candidateCount` held on that run; it reads
`OK` in all 96 rows. `bam_mau` is a hash of the sorted patterns that run wrote: within each of the
8 configurations, all runs of all three variants have the same hash, which is how the claim that
reordering the filters changes nothing was established rather than assumed. `khop_mau` compares
that hash with the pattern file of the corrected build where one exists; that is the case for 21
rows, on `accidents_negative` and `pumsb_negative`, and they all match. The other 75 rows, on
`mushroom_negative`, have no such reference and rely on the agreement between variants.

The four figures are not drawn by hand: `analysis/ve_hinh.py` reads those same CSV files with
`csv.DictReader` and redraws all four from them, so a figure cannot drift away from the
measurement behind it.

Counts are deterministic. Re-running any command in section 3 or section 5 reproduces the pattern
counts, the candidate counts and the pruning counters exactly, to the digit. Only the wall-clock
and CPU times differ, and section 6 explains how far those can be trusted.

`tools/chay_e8.ps1`, `tools/chay_pumsb.ps1` and `tools/chay_do_luong.ps1` are **resumable**: a
configuration whose console log already records a finished run is skipped, so an interrupted sweep
can simply be started again. Both are long —
the full E8 sweep is 96 runs and the pumsb sweep with the order of the code took several days of
wall-clock time (with `-ban duong_truoc`, about 27 minutes for all five levels).
`chay_do_luong.ps1` names its files after the dataset, the build and `minUtil`, and adds the four
periodicity thresholds to the name whenever they differ from the dataset's setting in Table 8 of the
paper, so two settings never share a log: at `minUtil` 19,000,000 on `accidents_negative`, `minAvg` 5
writes `accidents_f_19000000` and `minAvg` 1 writes `accidents_f_19000000_p1-2000-1-1000`. The build is
the letter after the dataset: `o` published, `f` patched, `d7` and `dt` the two item-order variants.
With `-chay_lai` a finished configuration is run again into new files with the suffix `_r2`, `_r3`,
and so on, so the log that an earlier row of `do_luong.csv` names is never overwritten. The run of
18 October at `minAvg` 1 predates this convention and is named `accidents_f_19000000_minavg1`.

## 6. Four environment traps

These cost us a working day each; they are recorded so nobody repeats them.

1. **A path containing Vietnamese characters breaks SPMF.** The project root is `D:\Dự án CNTT`.
   Any **absolute** path handed to SPMF is reported as `The input file does not exist` even though
   the file is there, because Java decodes command-line arguments with the native Windows code page
   rather than UTF-8. Always `cd` to the project root and use relative paths such as `data/...`.
   Where an absolute path is unavoidable, the PowerShell drivers convert it to its 8.3 short form
   with `(New-Object -ComObject Scripting.FileSystemObject).GetFile($p).ShortPath`, giving
   `D:\DNCNTT~1\...`.
2. **Out of memory.** On the large databases, put `-Xmx6g` immediately after `java`, as every
   measurement of the report did.
3. **The console perturbs the measurement.** `AlgoPHMN` prints a counter to `System.out` every
   10,000 candidates. `ClientAblationPHMN` silences `System.out` for the duration of the run so the
   printing is not timed.
4. **`java` on this machine is a shim.** `C:\Program Files\Common Files\Oracle\Java\javapath\java.exe`
   launches the real JVM as a **child** process, so reading the CPU time of the process you started
   always yields about 0.05 s. The drivers locate the child PID with
   `Get-CimInstance Win32_Process -Filter "ParentProcessId=..."` and sample that instead. CPU time
   is also the only quantity immune to the machine sleeping, which it does whenever the lid closes.
   It is **not** immune to CPU frequency scaling: lock the clock with
   `powercfg /setactive 8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c` before any timing is treated as a
   result.

## 7. Datasets

`data/` holds the databases in SPMF's utility format, one transaction per line:

```
items : transaction utility : utility of each item
```

Negative values in the third field are the negative utilities the paper is about.

| File | Transactions | In repository |
|---|---|---|
| `PHMN_Table1_example.txt` | 8 | yes — the worked example of the paper |
| `strategy4_counterexample.txt` | 2 | yes — the counterexample to Strategy 4 of the paper |
| `DB_UtilityPerHUIs.txt`, `crisp_negative_RU.txt` | small | yes — regression fixtures |
| `chess_negative.txt` | 3,196 | yes |
| `mushroom_negative.txt` | 8,124 | yes |
| `pumsb_negative.txt` | 49,046 | yes — 27 MB |
| `accidents_negative.txt` | 340,183 | yes — 71 MB |
| `online_retail_negative.txt` | 17,780 | yes — built by us, see below |

| `uci_online_retail.zip` | 541,909 invoice lines | yes — the source, unchanged, 23 MB |

`accidents_negative.txt` and `pumsb_negative.txt` are the databases the paper itself uses. They are large but still below GitHub's
100 MB per-file limit, so the repository needs no Git LFS and a plain clone brings everything.
The utilities of the four SPMF benchmark files are synthetic, as the SPMF dataset page states, and
their line order is not a time order.

`online_retail_negative.txt` is a real N-database built for this project from the Online Retail
dataset: Chen, D. (2015). Online Retail [Dataset]. UCI Machine Learning Repository.
https://doi.org/10.24432/C5BW33, licence CC BY 4.0. `tools/sinh_online_retail.py` converts the
archive with the Python standard library only. A transaction is one customer in one ISO week, in
calendar order; the utility is quantity x unit price in pence (revenue: the source has no cost
price); a negative line (return, discount, fee) on product p becomes the separate item `NEG:p`, so
no item carries both signs; lines without a CustomerID are dropped. The reasons are in the
docstring of the script and in Section 6.4 of the report, and every count is in
`output/runs/sinh_online_retail.log`.

### Pattern files, and why there are 39 of them rather than 224

The experiments wrote 224 pattern files totalling 183 MB, but only **39 distinct contents**. The
repeated runs of E8 produce byte-identical output — which is exactly the invariant E8 set out to
test — and the runs of the published build produce empty files, which is the evidence that it finds
nothing. The repository therefore holds one representative of each distinct content, 17.4 MB, plus
`output/MANIFEST_output.csv`, which lists all 224 original names with their size, MD5 and the
representative that carries their bytes; the representative is a run of the patched build (`_f_`)
whenever its group has one. Nothing is lost: the manifest proves which file equals which.
Rebuild it, and the matching exception list in `.gitignore`, with:

```
py -I tools/manifest_output.py
```

Every *measured number* lives in the CSV files, which are committed in full, `output/do_luong.csv`,
`output/e8_do_luong.csv` and `output/runs/cpu_watch.csv`, or in the console logs of `output/runs/`.
Those, not the pattern files, are what the figures and tables of chapter 7 are built from.
