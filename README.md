Course project, *Dự Án CNTT*, Faculty of Information Technology, Ton Duc Thang University,
academic year 2026-2027, semester 1.

| Studied paper (F0) | Lai, Zhang, Chen, Gan, *A study of algorithms for mining periodic high-utility itemsets with both positive and negative utilities* (2023) |
| Algorithms under study | PHMN and PHMN+, as published in SPMF 2.66 |

The project does **not** re-implement PHMN. Following the supervisor's direction, it takes the
authors' own implementation as the ground truth, decomposes it into its eleven components, and
measures what each component actually contributes. Along the way the published implementation
turned out to contain a correctness bug; the repository contains the patch, the proof that the
patch is correct, and the experiments that quantify the consequences.

The written report is `523H0159_523H0169_week9.docx`. Chapter 7 of that report contains every
number produced by the code in this repository.

## 3. Quick start — reproduce the three headline results

### 3.1 Compile the patched classes

```
javac -nowarn -cp tools/spmf/spmf.jar -d build/patched src/patched/ca/pfv/spmf/algorithms/frequentpatterns/phmn_plus/*.java
```

This writes eight `.class` files into `build/patched`. Nothing inside `spmf.jar` is modified; the
patched build is selected by putting `build/patched` **first** on the classpath, so Java loads it
instead of the copy in the jar. That is the only trick used throughout the project.

### 3.2 Reproduce the worked example of the paper — expect exactly 5 patterns

```
java -jar tools/spmf/spmf.jar run PHMN data/PHMN_Table1_example.txt output/t1.txt 30 1 5 1 3
```

The five trailing numbers are, in order, `minUtil minPer maxPer minAvg maxAvg`.

### 3.3 The bug — the published build returns nothing on real data

```
java -Xmx4g -cp "tools/spmf/spmf.jar" ca.pfv.spmf.gui.Main run PHMN data/chess_negative.txt output/stock.txt 80000 1 3196 1 3196
```

`output/stock.txt` is empty: **0 patterns**.

### 3.4 The patch — same data, same parameters, many patterns

```
java -Xmx4g -cp "build/patched;tools/spmf/spmf.jar" ca.pfv.spmf.gui.Main run PHMN data/chess_negative.txt output/patched.txt 80000 1 3196 1 3196
```

The two commands differ **only** in `-cp`. The console banner reads `v2.38-PATCHED` when the
patched build is loaded, so there is never any doubt about which one ran.

### 3.5 Proof that the patch is correct, not merely more productive

```
py -I analysis/spmf_phmn_stress_test.py tools/spmf/spmf.jar
py -I analysis/spmf_phmn_stress_test.py tools/spmf/spmf.jar --patched build/patched
```

The script generates 60 small databases, enumerates **every** itemset by brute force to obtain the
ground truth, and compares. Expected outcome: the published build misses 213 of 1,224 true
patterns; the patched build matches the brute-force answer **100%**, with no missing and no spurious
pattern. Runtime about two to three minutes.

## 4. The patch

Three files, 67 changed lines, all of them restoring definitions the paper states but the code does
not implement.

**Root cause.** PHMN prunes a branch by computing an upper bound on the utility attainable in that
branch and discarding the branch when the bound falls below `minUtil`. A bound is only valid if it
is never lower than the real value. The published code builds the bound as `U + RU`, and lets the
**negative** utilities of items not yet added to the itemset enter `RU`. The bound then sinks below
the true utility and correct answers are pruned away. Definition 8 of the paper in fact prescribes
`PU + RU`, where `PU` is the sum of the *positive* utilities only.

**Concrete instance.** On `chess_negative`, item 46 has a true utility of 84,390 and occurs very
regularly, but the bound the published code computes for it is **−354,580**, so its whole branch is
cut. At `minUtil` 80,000 the published build therefore reports 0 patterns.

**The fix.**

* `ElementPHMN.java` — a new final field `putils` holding the positive utility of the itemset in
  that transaction, plus a four-argument constructor. The three-argument constructor is kept so
  that unrelated SPMF code still compiles.
* `UtilityListPHMN.java` — accumulate `sumPutils` alongside `sumIutils`.
* `AlgoPHMN.java` — one single root cause surfacing in five places: only positive utilities may
  enter `remainingUtility`; the TWU used by EUCP is the positive transaction utility; the subtree
  gate and the LA-prune accumulator both use `sumPutils + sumRutils`; and `putils` is maintained
  additively when utility lists are joined. The version banner becomes `v2.38-PATCHED`.

To see the patch itself:

```
diff -u tools/spmf/source/ca/pfv/spmf/algorithms/frequentpatterns/phmn_plus/AlgoPHMN.java src/patched/ca/pfv/spmf/algorithms/frequentpatterns/phmn_plus/AlgoPHMN.java
```

### Every number in the report can be traced back, and checked

Chapter 7 of the report states no number that is not also in this repository, and nothing in it was
transcribed by hand.

`output/do_luong.csv` holds one row per measured run. Besides the parameters and the results, each
row carries a `file_mau` column naming the pattern file that run produced and a `file_log` column
naming its raw console log, so any single figure in the report can be followed back to the output
of the program that produced it. `output/runs/` holds 206 such logs.

`output/e8_do_luong.csv` does the same for the 96 runs of experiment E8, and adds the pruning
counters. Two of its columns exist purely to be checked. `bat_bien` records whether the program's
own self-test `pairsConsidered = rejEUCP + rejESCP + candidateCount` held on that run; it reads
`OK` in all 96 rows. `bam_mau` is a hash of the patterns that run wrote, and `khop_mau` compares
that hash against the corrected build, which is how the claim that reordering the filters changes
nothing was established rather than assumed.

The four figures are not drawn by hand either: `analysis/ve_hinh.py` reads those same CSV files
with `csv.DictReader` and redraws all four from them, so a figure cannot drift away from the
measurement behind it.

Counts are deterministic. Re-running any command in section 3 or section 5 reproduces the pattern
counts, the candidate counts and the pruning counters exactly, to the digit. Only the wall-clock
and CPU times differ, and section 6 explains how far those can be trusted.

`tools/chay_e8.ps1` and `tools/chay_pumsb.ps1` are **resumable**: a configuration whose output file
already exists is skipped, so an interrupted sweep can simply be started again. Both are long —
the full E8 sweep is 96 runs and the pumsb sweep took several days of wall-clock time.

## 6. Four environment traps

These cost us a working day each; they are recorded so nobody repeats them.

1. **A path containing Vietnamese characters breaks SPMF.** The project root is `D:\Dự án CNTT`.
   Any **absolute** path handed to SPMF is reported as `The input file does not exist` even though
   the file is there, because Java decodes command-line arguments with the native Windows code page
   rather than UTF-8. Always `cd` to the project root and use relative paths such as `data/...`.
   Where an absolute path is unavoidable, the PowerShell drivers convert it to its 8.3 short form
   with `(New-Object -ComObject Scripting.FileSystemObject).GetFile($p).ShortPath`, giving
   `D:\DNCNTT~1\...`.
2. **Out of memory.** On the large databases, put `-Xmx4g` immediately after `java`.
3. **The console perturbs the measurement.** `AlgoPHMN` prints a counter to `System.out` every
   10,000 candidates. `ClientAblationPHMN` silences `System.out` for the duration of the run so the
   printing is not timed.
4. **`java` on this machine is a shim.** `C:\Program Files\Common Files\Oracle\Java\javapath\java.exe`
   launches the real JVM as a **child** process, so reading the CPU time of the process you started
   always yields about 0.05 s. The drivers locate the child PID with
   `Get-CimInstance Win32_Process -Filter "ParentProcessId=..."` and sample that instead. CPU time
   is also the only quantity immune to the machine sleeping, which it does whenever the lid closes.
   It is **not** immune to CPU frequency scaling: lock the clock with
   `powercfg /setactive 8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c` before any timing is treated as a
   result.

## 7. Datasets

`data/` holds the databases in SPMF's utility format, one transaction per line:

```
items : transaction utility : utility of each item
```

Negative values in the third field are the negative utilities the paper is about.

| File | Transactions | In repository |
|---|---|---|
| `PHMN_Table1_example.txt` | 7 | yes — the worked example of the paper |
| `DB_UtilityPerHUIs.txt`, `crisp_negative_RU.txt` | small | yes — regression fixtures |
| `chess_negative.txt` | 3,196 | yes |
| `mushroom_negative.txt` | 8,124 | yes |
| `pumsb_negative.txt` | 49,046 | yes — 27 MB |
| `accidents_negative.txt` | 340,183 | yes — 71 MB |

The last two are the databases the paper itself uses. They are large but still below GitHub's
100 MB per-file limit, so the repository needs no Git LFS and a plain clone brings everything.

### Pattern files, and why there are 15 of them rather than 140

The experiments wrote 140 pattern files totalling 166 MB, but only **15 distinct contents**. The
repeated runs of E8 produce byte-identical output — which is exactly the invariant E8 set out to
test — and the runs of the published build produce empty files, which is the evidence that it finds
nothing. The repository therefore holds one representative of each distinct content, 11.7 MB, plus
`output/MANIFEST_output.csv`, which lists all 140 original names with their size, MD5 and the
representative that carries their bytes. Nothing is lost: the manifest proves which file equals
which. Rebuild it, and the matching exception list in `.gitignore`, with:

```
py -I tools/manifest_output.py
```

Every *measured number* lives in the CSV files, which are committed in full: `output/do_luong.csv`,
`output/e8_do_luong.csv` and `output/runs/cpu_watch.csv`. Those, not the pattern files, are what
the figures and tables of chapter 7 are built from.
